title: Evaluation, deployment and recovery
---

An evaluator receives a snapshot of an immutable candidate and an AbortSignal. It
returns `{passed: boolean, metrics?: Record<string, number>, notes?: string}`.
Metrics must be finite. Supply `evaluator`, `version` and `datasetHash` in its context.
Keep held-out examples disjoint from proposal/correction examples by episode, entity
and time. Freeze the split before generating proposals. Repeated tuning against one
holdout leaks information; rotate a final audit set and version the evaluator.

The classification starter uses exact-match labels, per-class non-regression and fixed
guardrail cases. Labels, system instructions, evaluator code and acceptance thresholds
are outside the generated prompt fragment. The proposing model never grades itself.
Passing a tiny holdout is not statistical proof of safety or production improvement.

## DeploymentAdapter contract

Implement three async methods: `apply(request)`, `rollback(request)` and
`inspect(request)`. Requests contain the stable attempt, candidate, optional restore
candidate, `idempotencyKey` equal to attempt ID, and cancellation signal. Namespace is
present in the records; include it in your external idempotency/authorization scope.

Apply/rollback return a durable receipt with `attemptId`, `artifactVersion`, and
`previousArtifactVersion` (nullable for an empty baseline). Apply must return a
non-null version. Rollback must return exactly the recorded restore version.
Optional JSON metadata can hold external operation IDs; do not put secrets there.

Compare the current external version to `attempt.expectedArtifactVersion` before
changing it. Persist the receipt and change together when the external system allows.
Retrying the same idempotency key must return the same result, not apply again. Keep
enough history to restore the exact predecessor. Do not use “latest superseded” as a
rollback destination. Avoid out-of-band writes to a managed target.

## Pending outcomes are intentionally blocking

| Inspection result | Required meaning / SDK action |
| --- | --- |
| applied + valid receipt | Change definitely occurred; finalize lifecycle and active pointer atomically |
| not_applied | Change definitely did not occur **and cannot occur later**; clear reservation |
| unknown | Outcome is ambiguous; keep target blocked |

An empty lookup is not necessarily proof of non-application: an old request may still
be running. Before returning `not_applied`, fence the attempt so late operations with
that key cannot change the target. If your provider cannot prove/fence it, return
unknown and escalate through your application's operations process.

The SDK saves an attempt before dispatch, calls externally without a database
transaction, then saves the receipt/states/event/pointer atomically. If any boundary
fails, the error includes `code: 'deployment_pending'` and `attemptId`. A valid
receipt may already exist externally. Call `reconcileAttempt(id, adapter)`; it only
inspects, never blindly reapplies. Missing/malformed receipts remain pending.

## Rollback and operational checklist

Only the active deployed candidate can be rolled back. Its recorded predecessor
must still be eligible; rolled-back versions stay rolled_back. A → B → C followed
by rollback C then B restores B then A, never C again. The initial external baseline
may have no Loopiter candidate; its version is retained in the receipt.

For an incident: disable new deployments, list pending attempts/events, inspect
external receipts, reconcile, verify the serving version, and explicitly roll back
if needed. Resolve uncertainty before allowing another target change. Do not delete
attempts, edit active pointers manually or restore an old database snapshot while
external versions continue changing. Adapters must reconcile after a disaster restore.

Manual and controller-driven deployment use the same core implementation. Loopiter
coordinates retry-safe operations; it does **not** claim universal exactly-once
execution across databases and arbitrary external systems.
